# 业务不变量记忆

这些约束用于防止局部代码“看起来能跑”却破坏订单、支付、库存和权限的一致性。修改相关流程前必须重新核对源码和 migration。

## 数据所有权

- 服务独占自己的数据库和事务；禁止跨库直接读写。
- 商品、购物车、地址、订单、库存、支付、通知分别由对应服务拥有。
- 跨服务事实通过 API、共享 contract 和事件传递；接收方保留自己所需的业务快照。

## 结算单、子订单与支付

- 一次结算生成 checkout/order 级主记录，并按商家拆分子订单和订单项。
- 一次结算只产生一笔真实支付；支付金额再分摊到子订单。不要为每个子订单重复创建真实支付。
- 退款同样围绕支付和子订单分摊记录处理，不能只修改订单状态而丢失支付侧退款账。
- 金额以明确的精度和舍入规则计算；总支付、子订单分摊、退款分摊必须可对账。

## 库存预占生命周期

- 创建订单流程先向库存服务申请预占，再持久化本地订单。
- 若本地订单持久化失败，未绑定的预占必须可超时过期或被补偿释放。
- 本地事务提交后再绑定预占与订单，避免库存持有指向尚未提交的订单。
- 支付成功后的可靠事件推进库存确认；取消、超时或失败路径可靠释放预占。
- 预占、绑定、确认和释放均需要幂等键/状态检查，重复请求不能重复扣减或释放。

## 状态机与并发

订单状态当前包括：

```text
CREATED -> STOCK_RESERVED -> STOCK_DEDUCTED -> WAIT_PAY -> PAID
PAID -> INVENTORY_CONFIRMING -> WAIT_SHIP -> SHIPPED -> RECEIVED -> COMPLETED
```

失败和补偿状态包括 `INVENTORY_CONFIRM_FAILED`、`CANCELLED`、`FAILED`、`REFUND_REQUIRED`、`REFUNDED`。这不是任意可达图；具体合法迁移以当前 domain service 为准。

支付状态当前包括 `WAIT_BUYER_PAY`、`TRADE_SUCCESS`、`TRADE_CLOSED`、`TRADE_FAILED`。

- 更新状态时条件中包含期望旧状态，检查受影响行数，并记录状态日志。
- 回调、轮询和消息可能乱序或重复；已到终态的数据不能被较旧事件回退。
- 新增状态必须同步检查枚举、domain transition、mapper、查询条件、日志、事件消费者和对账任务。

## Outbox 与外部副作用

- 本地状态变化与 Outbox event 在同一数据库事务中提交。
- Relay 负责发送、重试和记录结果；消费者以稳定事件 ID/业务键幂等。
- 通知、库存确认/释放、退款推进等关键动作不能依赖“事务内调用一次 Feign 就一定成功”。
- 如果外部调用必须先发生，设计可恢复的孤儿资源回收或补偿流程。

## 身份与资源归属

- 角色为 `ADMIN`、`CUSTOMER`、`MERCHANT`，权限常量集中在 `commerce-contracts` 的安全包。
- Gateway 的角色校验不是资源授权的替代。业务服务还要校验订单、购物车、地址、Session、Run 等是否属于当前用户/商家。
- 服务间传播使用 `SecurityHeaders`；不要把前端随意传入的 userId 当作可信身份。
- 管理员跨用户访问必须是显式规则，不能由空 userId、缺失 header 或异常分支意外获得。

## 当前实现与规划

- MES、完整物流编排等内容在业务文档中可能是规划方向，不代表已有可调用实现。
- 若需求依赖规划能力，先指出缺失的模块、contract、数据模型和补偿策略，再实施用户明确要求的范围。
